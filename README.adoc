== Result (4 CPU / 4 GiB containers)

Every demo is built into its own Docker image and benchmarked in a container capped at *4 CPU cores
and 4 GiB RAM*, with `ab` pinned to a different set of cores so the load generator cannot compete
with the server for CPU. Unlike the original run, every framework is asked for the *same 20 rows* of
the same `content -> category -> parent` query, and the report prints the row count and payload size
per framework so an unfair row is visible rather than hidden.

The harness picks the container's cores itself: `--cpus N` claims *N physical cores, one hardware
thread each*, preferring efficiency cores. On a hybrid CPU a naive `--cpuset-cpus=0-3` would hand the
server 4 hyperthreads on only 2 performance cores -- less throughput than the number suggests, and
much noisier, because performance cores swing with boost clocks and package temperature. Efficiency
cores hold a flatter clock, so repeat runs agree with each other.

CAUTION: `--cpuset-cpus` *confines* the container to those cores, it does not *reserve* them. Your
own processes can still be scheduled there, and L3 cache, memory bandwidth and the package power
budget are shared no matter how the pinning is set. Treat a run taken on a busy desktop as
indicative, not authoritative.

[source,shell]
----
./run.sh                        # build + benchmark everything, write the report
./run.sh --only rust,java       # just those
./run.sh -n 2000 -c "1 10 100"  # quicker pass
./run.sh --cpus 2 --memory 2g   # different caps
./run.sh --native               # run on the host instead of in containers
./run.sh --list                 # show what was discovered
----

== Adding a framework

Each `demo-*/` directory owns two files and is customizable on its own:

`run.sh`::
The single source of truth for that framework's port and benchmark URL. Four subcommands:
`meta` (prints `NAME=`, `STACK=`, `PORT=`, `BENCH_PATH=`), `check` (is the toolchain present?),
`build`, and `start` (exec the server in the foreground on `$PORT`).

`Dockerfile`::
Built with the *repo root as context* (`docker build -f demo-x/Dockerfile .`) so it can
`COPY demo.sqlite`. Lays the app out at `/app/demo-x/` with the database at `/app/demo.sqlite`,
and ends in `CMD ["./run.sh", "start"]`.

The root `run.sh` discovers `demo-*/run.sh` automatically, so a new directory following that
contract needs no changes to the harness.
