== Result (4 CPU / 4 GiB containers)

Every demo is built into its own Docker image and benchmarked in a container capped at *4 CPU cores
and 4 GiB RAM*, with the load generator pinned to a different set of cores so it cannot compete with
the server for CPU.

The load is a *weighted mix* driven by k6 (`bench/mixed.js`), not a single URL, so response sizes
vary within a run the way they would in production:

[cols="<10,<34,<30",options="header"]
|===
| Weight | Request | Response

| 55% | list, `size=20`            | ~4 KB
| 15% | list, `size=1`             | a few hundred bytes
| 10% | list, `size=100`           | ~20 KB
| 15% | single item, random id     | ~200 bytes
| 5%  | all categories             | 100 rows, ~14 KB
|===

==== Dataset

`demo.sqlite` is generated by `db/generate.sql` and is fully deterministic:

[source,sh]
----
rm -f demo.sqlite && sqlite3 demo.sqlite < db/generate.sql
----

* *100 categories in 3 levels* (10 roots, 30 children, 60 grandchildren). Ids spell the path:
  `2` Technology > `21` Artificial Intelligence > `211` Large Language Models.
* *100,000 contents*, spread so that every page mixes all three levels; every 1000th has no category.
* Every nested category in a response carries its parent chain all the way to the root.

The same file is the fixture for every demo's endpoint tests: each `demo-*/` has the same 16 cases
(list paging, item at each depth, not found, invalid input, update, categories) with the full
expected JSON written out. Each demo's tests run in their own container, built from the `test`
stage of its Dockerfile with `demo.sqlite` copied in, so no run touches the repo's file or shares a
database with another demo:

[source,sh]
----
./test.sh              # all demos
./test.sh go rust      # just those
----

Benchmarks are isolated the same way: in Docker mode each framework runs in a fresh container with
its own baked-in copy, and `--native` mode hands every framework a fresh temporary copy.

Every framework gets the identical mix against the identical database, and the report records
p50/p95/p99 latency per level alongside throughput. A level counts as `Failed` when more than 1% of
requests come back non-2xx. `./run.sh --loadgen ab` falls back to the old single-URL `ab` profile.

The harness picks the container's cores itself: `--cpus N` claims *N physical cores, one hardware
thread each*, preferring efficiency cores. On a hybrid CPU a naive `--cpuset-cpus=0-3` would hand the
server 4 hyperthreads on only 2 performance cores -- less throughput than the number suggests, and
much noisier, because performance cores swing with boost clocks and package temperature. Efficiency
cores hold a flatter clock, so repeat runs agree with each other.

CAUTION: `--cpuset-cpus` *confines* the container to those cores, it does not *reserve* them. Your
own processes can still be scheduled there, and L3 cache, memory bandwidth and the package power
budget are shared no matter how the pinning is set. Treat a run taken on a busy desktop as
indicative, not authoritative.

[source,shell]
----
./run.sh                        # build + benchmark everything, write the report
./run.sh --only rust,java       # just those
./run.sh -n 2000 -c "1 10 100"  # quicker pass
./run.sh --cpus 2 --memory 2g   # different caps
./run.sh --native               # run on the host instead of in containers
./run.sh --list                 # show what was discovered
----

Everything between the markers below is written in place by `./run.sh` (and also saved standalone
as link:report.adoc[report.adoc]). Edit the harness, not this text.

NOTE: the ephemeral port range above caps how many sockets the load generator can hold

concurrency level can therefore run into a client-side kernel limit rather than a server
limit, which is one reason a `Failed` there should not be read as a framework verdict. k6
reuses connections by default, so it is far less exposed to this than non-keepalive `ab`.

=== Reading these numbers

* Each framework gets the *same weighted mix* of three endpoints and three page sizes,
  so response sizes vary from a few hundred bytes to ~20 KB within a single run. The
  per-framework Bytes column below is the size=20 list response, used as a sanity check
  that every framework returns the same 20 rows.
* A level counts as Failed when more than 1% of requests are non-2xx.
* Query _count_ is an ORM property, not a language property: Hibernate's entity graph
  resolves the nested parent in one join, while Prisma, Django and SeaORM issue a second
  query for it. That shows up here as a framework difference.
* Only one server runs at a time, and each container is removed before the next starts.
* k6 is multi-threaded and runs in its own container pinned to the cores the server is
  not using, so it is far less likely to be the bottleneck than `ab` was.
* Peak RSS is the container's cgroup `memory.peak`, so it includes the runtime, not just
  the heap.
* Raw ab output per level is under `.bench-logs/`.

== Adding a framework

Each `demo-*/` directory owns two files and is customizable on its own:

`run.sh`::
The single source of truth for that framework's port and benchmark URL. Four subcommands:
`meta` (prints `NAME=`, `STACK=`, `PORT=`, `BENCH_PATH=`), `check` (is the toolchain present?),
`build`, and `start` (exec the server in the foreground on `$PORT`).

`Dockerfile`::
Built with the *repo root as context* (`docker build -f demo-x/Dockerfile .`) so it can
`COPY demo.sqlite`. Lays the app out at `/app/demo-x/` with the database at `/app/demo.sqlite`,
and ends in `CMD ["./run.sh", "start"]`.

The root `run.sh` discovers `demo-*/run.sh` automatically, so a new directory following that
contract needs no changes to the harness.

NOTE: `demo-graalvm` holds no Java source of its own. Its `Dockerfile` compiles a native image from
`demo-hibernate-sqlite`'s sources, so the GraalVM row and the OpenJDK row are the *same application*
differing only in how it was compiled.

Each `run.sh` also publishes `LIST_PATH`, `ITEM_PATH` and `CATEGORIES_PATH` templates (with `{size}`
and `{id}` placeholders), which is how one k6 script drives frameworks that spell their endpoints
differently.
